* About this document
This is the verified inventory behind sqlite-cljs: which Node SQLite driver to wrap, what
that driver's API really does, which SQLite DDL/DML grammar the data-driven DSL must
render, which PRAGMAs a client library needs, and the exact DSL shapes the library
implements. It fixes contracts, not code.

*Product constraints that shape everything below (user directive):* ClojureScript-only
API (no =^js= hints, no interop at call sites, all interop in ONE driver namespace);
kebab-case keyword maps in and out; promesa promises for async operations; zero runtime
npm dependencies beyond the wrapped driver; values are ALWAYS bound parameters and
identifiers are ALWAYS quoted (SQL-injection safety is a hard rule).

* 0b. Implementation notes (2026-09-25)
The code follows this document; where implementation contradicted or
refined it, the section text below was corrected in place and the change is listed here.
- *Namespaces* (§9): the planned =driver= + =core= pair is ONE namespace, =sqlite-cljs.core=
  (task directive: exactly one driver-binding namespace). The execute layer is
  =sqlite-cljs.query=; the DML renderer is =sqlite-cljs.dsl= (planned as =query=); =ddl= and
  =migrate= as planned. No =^js= hints anywhere: driver properties are read with
  =unchecked-get= and methods called with =js-invoke= (the =util= precedent).
- *Constructor is synchronous*: =(core/db path-or-opts)= returns the db value map (task
  signature) — every operation on it returns a settled promesa promise.
- *Column option spelling* (§6.3.1): canonical keys are =:primary-key? :not-null? :unique?
  :autoincrement?=, =:references {:table :column :on-delete :on-update :deferrable}=,
  =:generated-as {:expr :stored?}= (task deliverable spec, consistent with =:strict?=); the
  bare spellings shown originally are accepted as aliases.
- *Defaults*: =:if-not-exists?= defaults to TRUE for every CREATE and =:if-exists?= to TRUE
  for every DROP (idempotent =migrate!=); the original text said false.
- *DDL output*: =ddl/render= returns ={:statements ["sql" ...]}= (strings; DDL never has
  parameters) instead of =[{:sql ..} ...]=.
- *STRICT/type validation errors* are =:sqlite-cljs/argument-error= carrying =:column= (task
  directive); malformed DSL forms remain =:sqlite-cljs/dsl-error= with =:form=.
- *Nested =transact!= is rejected* (=:reason :nested-transaction=, task directive) instead of
  becoming a SAVEPOINT (§2.5 describes the driver capability, unused).
- *migrate!* (§6.4) is an idempotent "bring the database up to these definitions" apply
  with drift detection and =user_version = (count defs)= as a fingerprint (task
  directive), not the versioned up/down runner originally proposed.
- *Reads*: =:coerce= per query implements uncertainty §8.4 option (b).
- *Large IN lists* (§8.14): above 500 values =[:in x coll]= renders
  =x IN (SELECT value FROM json_each(?))= with one JSON parameter; bulk inserts above 32766
  parameters are chunked transparently by =query/execute!= in one transaction.
- *DELETE/UPDATE grammar* (§5.5): with =ENABLE_UPDATE_DELETE_LIMIT=, =RETURNING= must come
  BEFORE =ORDER BY ... LIMIT= (=(local)= the other order is a syntax error).
- *readonly =:memory:=* (§2.1): the driver throws =TypeError "In-memory/temporary databases
  cannot be readonly"= =(local)=; =core/db= raises config-error before calling it.
- *Keywords as values*: in the DSL a keyword is always an identifier (dsl-error only when
  a value is required and cannot be bound); in raw ={:sql :params}= / =[sql & params]=
  calls a keyword parameter binds as its name (task directive).
- *Select items*: a two-element vector is ALWAYS =[expr alias]= (honeysql rule); bare
  function calls are wrapped =[[:lower :name]]= or written =[:as [:lower :name] :lname]=;
  =[:count :*]= is the documented exception. Same rule for =:order-by= items
  (=[[:lower :email] :asc]=).
- *Index expressions* (§6.3.2) render without extra parentheses.

** 1.4 Decision: better-sqlite3 13.x (runner-up node:sqlite; node-sqlite3 rejected)
Justification, in order of weight:
1. *Stability of the surface.* better-sqlite3 is a mature 13.x with a stable documented
   API; =node:sqlite= on the Node line we run (22.x) is officially experimental (1.1),
   prints a warning on every start, and its API grew feature by feature across 22.x
   minors (§1.2). A library that pins Node 22 cannot promise the runner-up's behaviour.
2. *Feature completeness for this library.* better-sqlite3 has the =transaction(fn)=
   wrapper with savepoint nesting and deferred/immediate/exclusive variants (§2.5), a
   =pragma()= helper, =pluck/raw/expand=, =safeIntegers= per statement, =backup=,
   =serialize=, UDFs/aggregates/virtual tables; =node:sqlite= v22 has no transaction
   helper and no pragma helper.
3. *Install story.* 13.0.0 moved to N-API with prebuilds inside the package: on this
   machine (Node 22.23.2, linux-x64) install was a pure tarball extraction, no toolchain
   needed (§1.3). Eight platform/arch prebuilds cover the house targets.
4. *Adoption.* 7.36 M downloads/week vs 1.83 M for the deprecated =sqlite3= (npm).
5. *node-sqlite3* is out: its own README declares it deprecated and unmaintained, and
   its callback-era async API contradicts the driver's own guidance ("mutex thrashing";
   (docs bs3 README "Why should I use this instead of node-sqlite3")).
Risks accepted (tracked in §8): native addon (rebuild needed for Electron/unsupported
platforms), SQLite version pinned by the driver's release cadence, engines =>= 22=.
Runner-up plan: the driver namespace (§9.1) is the only place that knows the driver; a
=node:sqlite= binding of the same ~20 functions is feasible later (differences in §2.9),
which is why the surface deliberately avoids driver-specific extras (=expand=, virtual
tables) in the public API.

** 1.5 Async policy (house rule: promesa promises)
better-sqlite3 is synchronous by design (its README argues this gives *better*
concurrency for an embedded engine). The public =core= functions return promesa promises
that are *already resolved/rejected* from the synchronous call — documented as such:
they never yield to the event loop, exceptions become rejections, and =transact!= runs
its body synchronously inside the driver's transaction wrapper (an async body would
commit before its first =await=; (docs bs3 api.md transaction caveats)). Genuinely async
driver operations (=backup=) return the driver's promise wrapped in promesa. Long queries
block the event loop; the documented escape is a worker thread (§2.7), out of scope.

** 2.5 Transactions (docs bs3 api.md; docs sqlite lang_transaction; local)
- =db.transaction(fn)= returns a function that runs =fn= inside =BEGIN ... COMMIT=,
  rolling back and rethrowing on any throw (=(local)= an insert that violates UNIQUE
  inside the wrapper leaves the count unchanged). Variants =.deferred= (=BEGIN=, the
  default), =.immediate=, =.exclusive=. Arguments and return value are forwarded.
- Nested transaction functions become =SAVEPOINT=s; an inner throw rolls back to its
  savepoint only (=(local)= outer insert survives an inner failure that the outer catches).
- Rules: never mix manual BEGIN/COMMIT with the wrapper; async functions are wrong (commit
  happens at the first =await=); after catching an error *inside* a transaction check
  =db.inTransaction= — SQLite may have rolled back on its own (=ON CONFLICT ROLLBACK=,
  =RAISE=, =SQLITE_FULL=, =SQLITE_BUSY=), and the recommended action is to rethrow.
- SQLite semantics: =DEFERRED= starts as a read transaction and upgrades on the first
  write (may then hit =SQLITE_BUSY= *mid-transaction*); =IMMEDIATE= takes the write lock at
  =BEGIN= (fails fast with BUSY, the busy handler waits); =EXCLUSIVE= = IMMEDIATE in WAL.
  House position (§7.6): =transact!= defaults to =:immediate=.
- =COMMIT= itself can fail with =SQLITE_BUSY= when another reader is active (rollback
  journal modes); in WAL a writer never waits for readers.

** 2.6 User-defined functions, aggregates, extensions
- =function= / =aggregate= (§2.1) receive JS numbers (BigInt with =safeIntegers: true=),
  strings, Buffers, null; the return value must be a bindable value (undefined → NULL).
  =directOnly: true= keeps them out of schema expressions (relevant to =trusted_schema=,
  §4.1). =(local)= the name =nothing= is an SQLite keyword (=DO NOTHING=) — UDF names must
  avoid keywords or be quoted.
- Extensions: =loadExtension= exists; compatibility is the caller's problem. JSON is
  built in (SQLite ≥ 3.38.0, =(local)= =json_extract=, =->>=, =json_group_array= work);
  FTS5, R-Tree, math functions are compiled in (§2.8).

** 2.7 Worker threads — out of scope, noted (docs bs3 threads.md)
better-sqlite3 supports one connection per worker thread (the doc's thread-pool example
posts ={sql, parameters}= messages). The library uses the main thread only; a worker mode
would be an additional entry point later (uncertainty §8.13).

* 3. SQLite DDL grammar census
Everything in this section is from the sqlite.org language reference (=(docs sqlite)=,
pages listed in §10) unless tagged =(local)= (verified against better-sqlite3 13.0.3 /
SQLite 3.53.4 on this machine). Version numbers are from https://sqlite.org/changes.html.
The DSL (§6) must render exactly these shapes and nothing else.

** 3.1 CREATE TABLE skeleton (docs lang_createtable)
#+begin_example
CREATE [TEMP|TEMPORARY] TABLE [IF NOT EXISTS] [schema.]name
  ( column-def [, column-def]* [, table-constraint]* )
  [table-options]                       -- WITHOUT ROWID and/or STRICT, comma separated
CREATE TABLE [IF NOT EXISTS] name AS select-stmt   -- no constraints, affinity from select
#+end_example
- =column-def ::= name [type-name] column-constraint*=
- =type-name= is any sequence of identifiers optionally followed by =(n)= or =(n,m)=; the
  numbers are ignored by SQLite (=VARCHAR(255)= is TEXT affinity, no length check)
  (docs datatype3 §3.1.1).
- =CREATE TABLE ... AS SELECT= yields columns without PRIMARY KEY, UNIQUE, NOT NULL or
  DEFAULT; declared types come from the expression affinity. The DSL should not offer
  it as a schema primitive (it is a data-copy tool); a =:raw= migration step covers it.
- The number of columns is bounded by =SQLITE_MAX_COLUMN= (2000 default, §5.9).

** 3.2 Column types and type affinity (docs datatype3)
SQLite is *dynamically typed*: the declared type only sets the column's affinity (a
preference), not a constraint, unless the table is STRICT (§3.3). Storage classes: NULL,
INTEGER (1..8-byte signed), REAL (8-byte IEEE), TEXT, BLOB.

| Rule | Declared type contains       | Affinity | Effect on inserted values                                                                 |
|------+------------------------------+----------+-------------------------------------------------------------------------------------------|
| 1    | "INT" (INT, INTEGER, BIGINT, INT8, UNSIGNED BIG INT ...) | INTEGER | text that is a well-formed number is converted (to INTEGER, else REAL); other text stays TEXT; REAL with integral value becomes INTEGER |
| 2    | "CHAR", "CLOB", "TEXT"       | TEXT     | numbers are converted to their text form                                                  |
| 3    | "BLOB" or *no type at all*   | BLOB     | nothing is coerced                                                                        |
| 4    | "REAL", "FLOA", "DOUB"       | REAL     | like NUMERIC but integers are stored as floating point                                    |
| 5    | anything else (NUMERIC, DECIMAL, BOOLEAN, DATE, DATETIME, ...) | NUMERIC | like INTEGER affinity (difference only visible in CAST) |

Rules are tried in order: "CHARINT" is INTEGER (rule 1 wins). Verified locally: binding
JS =5= into a TEXT column stores TEXT ='5'=; binding =5.0= into an INTEGER column stores
INTEGER 5 (JS cannot distinguish 5 from 5.0, both bind as REAL, then affinity converts)
=(local)=.

Consequences for the DSL (house positions in §7):
- =BOOLEAN= is *not* a storage class: booleans are integers 0/1; the =TRUE=/=FALSE=
  keywords exist since 3.23.0 and are literals 1/0 (docs datatype3 §2.1; docs quirks §3.1).
- No date/time storage class: TEXT ISO-8601 ("YYYY-MM-DD HH:MM:SS.SSS"), REAL Julian day
  or INTEGER unix seconds are the three formats the built-in date functions understand
  (docs datatype3 §2.2); =unixepoch()= exists since 3.38.0, the ='subsec'= modifier since
  3.42.0 (docs changes).
- The DSL type vocabulary should therefore be exactly =:integer :real :text :blob :any=
  (the STRICT set, §3.3) plus =:numeric= for non-strict tables, and it should render the
  type name verbatim in upper case. Any other keyword type (=:boolean=, =:datetime=,
  =:varchar=) should be rejected with a =:sqlite-cljs/dsl-error= rather than silently
  mapped, because in a STRICT table it would fail at CREATE time and in a non-strict
  table it silently becomes NUMERIC affinity (uncertainty §8.6 asks whether to allow a
  =[:raw "VARCHAR(10)"]= escape).

** 3.3 STRICT tables (docs stricttables) (SQLite ≥ 3.37.0, 2021-11-27)
- Append =STRICT= after the closing parenthesis. Every column must have a type and it
  must be one of =INT INTEGER REAL TEXT BLOB ANY= (no other names, no =VARCHAR(n)=).
- Values are coerced with the usual affinity rules; anything that cannot be converted
  losslessly raises =SQLITE_CONSTRAINT_DATATYPE= (=(local)=: inserting text ='abc'= into a
  STRICT INTEGER column → =SQLITE_CONSTRAINT_DATATYPE "cannot store TEXT value in INTEGER
  column n.x"=; inserting =5.0= into a STRICT INTEGER column succeeds and stores INTEGER;
  =5.5= is rejected).
- =ANY= keeps the value exactly as inserted (no numeric coercion of numeric-looking text,
  unlike =ANY= in a non-strict table).
- PRIMARY KEY columns are implicitly NOT NULL; an =INTEGER PRIMARY KEY= is still the
  rowid alias (an =INT PRIMARY KEY= is not).
- =PRAGMA integrity_check= verifies STRICT column types.
- A database containing a STRICT table cannot be opened by SQLite < 3.37.0 (unless
  =PRAGMA writable_schema=ON=). Both candidate drivers bundle ≥ 3.51 (§1).
- House position (§7.1): =:strict? true= is the *default* for tables created by the DSL;
  callers opt out with =:strict? false=.

** 3.4 Column constraints (docs lang_createtable §3)
| Constraint                          | Syntax rendered                                              | Notes                                                                                                                              |
|-------------------------------------+--------------------------------------------------------------+------------------------------------------------------------------------------------------------------------------------------------|
| PRIMARY KEY                         | =PRIMARY KEY [ASC|DESC] [conflict-clause] [AUTOINCREMENT]=   | at most one per table; =INTEGER PRIMARY KEY= = rowid alias (§3.6); =INTEGER PRIMARY KEY DESC= is *not* an alias (documented bug)   |
| NOT NULL                            | =NOT NULL [conflict-clause]=                                 | column-level only (no table-level NOT NULL)                                                                                         |
| UNIQUE                              | =UNIQUE [conflict-clause]=                                   | implemented as a unique index; NULLs are all distinct                                                                              |
| CHECK                               | =CHECK (expr)=                                               | expr may not contain a subquery; result cast to NUMERIC, 0 → violation, NULL → passes; conflict algorithm always ABORT             |
| DEFAULT                             | =DEFAULT literal | DEFAULT (expr) | DEFAULT CURRENT_TIME/CURRENT_DATE/CURRENT_TIMESTAMP= | the expr must be constant: no subqueries, column refs, *bound parameters* or double-quoted strings; =(local)=: =DEFAULT ?= → =SQLITE_ERROR=; CURRENT_TIMESTAMP is UTC text "YYYY-MM-DD HH:MM:SS" |
| COLLATE                             | =COLLATE name=                                               | built-ins BINARY (default), NOCASE (ASCII only), RTRIM                                                                              |
| REFERENCES (foreign-key-clause)     | =REFERENCES parent(cols) [ON DELETE action] [ON UPDATE action] [MATCH x] [[NOT] DEFERRABLE [INITIALLY DEFERRED|IMMEDIATE]]= | §3.7                                                                                            |

=conflict-clause ::= ON CONFLICT ROLLBACK|ABORT|FAIL|IGNORE|REPLACE= (§3.15); not allowed on
CHECK and FOREIGN KEY.

** 3.5 Table constraints (docs lang_createtable)
| Constraint  | Syntax                                                                       | Notes                                                                      |
|-------------+------------------------------------------------------------------------------+----------------------------------------------------------------------------|
| PRIMARY KEY | =[CONSTRAINT n] PRIMARY KEY (col [ASC|DESC] [COLLATE c], ...) [conflict-clause]= | column names only, no expressions; =PRIMARY KEY(x DESC)= on a lone INTEGER column still makes it the rowid alias |
| UNIQUE      | =[CONSTRAINT n] UNIQUE (cols) [conflict-clause]=                             | column names only (use CREATE UNIQUE INDEX for expressions)                 |
| CHECK       | =[CONSTRAINT n] CHECK (expr)=                                                | same rules as column CHECK                                                 |
| FOREIGN KEY | =[CONSTRAINT n] FOREIGN KEY (cols) foreign-key-clause=                       | composite keys must use this form                                          |

** 3.6 rowid, INTEGER PRIMARY KEY, AUTOINCREMENT (docs lang_createtable §5; docs autoinc)
- Every non-WITHOUT-ROWID table has a 64-bit signed =rowid= (aliases =oid=, =_rowid_=
  unless a real column has that name).
- A single-column PRIMARY KEY whose declared type is *exactly* =INTEGER= (any case) is an
  alias for the rowid; =INT=, =BIGINT=, etc. are ordinary columns with a unique index.
- The rowid alias must hold integers; inserting NULL auto-assigns (largest rowid + 1, or
  random above 2^63-1 exhaustion → =SQLITE_FULL=); inserting a blob/text that is not a
  lossless integer → "datatype mismatch" (=SQLITE_MISMATCH=).
- =AUTOINCREMENT= (only valid on =INTEGER PRIMARY KEY=, never on WITHOUT ROWID tables)
  changes the algorithm to "never reuse a rowid from a *committed* transaction", tracked
  in =sqlite_sequence=. The sqlite.org summary: "imposes extra CPU, memory, disk space,
  and disk I/O overhead and should be avoided if not strictly needed. It is usually not
  needed." House position (§7.2): the DSL renders =AUTOINCREMENT= only when asked
  (=:autoincrement true=) and the docstring repeats this warning.
- =lastInsertRowid= (driver) is meaningless for WITHOUT ROWID tables (=(local)=: it
  reports the unchanged previous rowid) — use =RETURNING= instead (§5.3).

** 3.7 Foreign keys (docs foreignkeys)
- Declared per column (=REFERENCES parent(col)=) or per table (=FOREIGN KEY (a,b)
  REFERENCES parent(x,y)=). The parent key must be named columns (never the rowid) and
  must be a PRIMARY KEY or UNIQUE *constraint* of the parent (a UNIQUE index created by
  CREATE INDEX also works but can be dropped silently — sqlite.org recommends
  constraints).
- Enforcement is a per-connection setting: =PRAGMA foreign_keys=ON=, default OFF in
  stock SQLite (quirks §4). Both candidate drivers turn it ON: better-sqlite3 compiles
  with =SQLITE_DEFAULT_FOREIGN_KEYS=1= (§2.8) and node:sqlite's
  =enableForeignKeyConstraints= defaults to true (§2.9) — =(local)= both report
  =foreign_keys = 1= on a fresh connection.
- =PRAGMA foreign_keys= is a *no-op inside a transaction* (docs pragma) (=(local)=:
  toggling it inside BEGIN..COMMIT leaves it at 1). Migrations that need it off must
  toggle it outside the transaction (§6.4).
- Actions for =ON DELETE= / =ON UPDATE=: =NO ACTION= (default), =RESTRICT= (checked
  immediately, even if deferred), =SET NULL=, =SET DEFAULT=, =CASCADE=.
- Deferral: =DEFERRABLE INITIALLY DEFERRED= is the only spelling that makes a constraint
  deferred (checked at COMMIT); all other combinations are immediate. =PRAGMA
  defer_foreign_keys=ON= defers all constraints for the current transaction.
- =MATCH= is parsed and ignored (always MATCH SIMPLE). A NULL child key never violates.
- Violation code: =SQLITE_CONSTRAINT_FOREIGNKEY= (787).
- DDL interplay (with enforcement ON): =ALTER TABLE ADD COLUMN ... REFERENCES= requires
  DEFAULT NULL; =DROP TABLE= runs an implicit =DELETE= first (actions fire, violations
  abort the drop); =RENAME TO= rewrites child REFERENCES (≥ 3.26.0 always).
- =PRAGMA foreign_key_check [(table)]= lists violations (child table, rowid, parent,
  fk id); =PRAGMA foreign_key_list(table)= lists declarations (=(local)= columns:
  =id seq table from to on_update on_delete match=).
- Child-key indexes are *not* created automatically; sqlite.org §3 recommends an index
  on every child key. House position (§7.3): the DSL adds nothing automatically but
  =ddl/lint= (§9) warns about un-indexed child keys.

** 3.8 Generated columns (docs gencol) (SQLite ≥ 3.31.0, 2020-01-22)
- =col TYPE [GENERATED ALWAYS] AS (expr) [VIRTUAL|STORED]=; VIRTUAL (computed on read)
  is the default; STORED is written to disk.
- May have a type (affinity applied to the result), NOT NULL, CHECK, UNIQUE, FK
  constraints and indexes (an index on a VIRTUAL column is an expression index).
- May not: have a DEFAULT, be part of the PRIMARY KEY, use subqueries/aggregates/window
  or non-deterministic functions, reference the rowid directly, depend on itself; every
  table needs at least one non-generated column.
- =ALTER TABLE ADD COLUMN= can add VIRTUAL but not STORED generated columns.
- =PRAGMA table_xinfo= exposes them (=hidden= = 2 virtual, 3 stored); =table_info= omits
  them.

| Option          | Since | Requirements / effects (docs withoutrowid; docs stricttables)                                                                                                     |
|-----------------+-------+------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| =WITHOUT ROWID= | 3.8.2 | requires a PRIMARY KEY (else error); the PK is the clustered b-tree key; =INTEGER PRIMARY KEY= loses its rowid-alias meaning; AUTOINCREMENT is an error; PK columns are NOT NULL enforced; =last_insert_rowid()= unaffected by inserts; best when the PK is not a large blob/string ("less than ~1/20th of a page") |
| =STRICT=        | 3.37.0| §3.3; both may be combined: =) WITHOUT ROWID, STRICT=                                                                                                            |

** 3.10 CREATE INDEX (docs lang_createindex)
#+begin_example
CREATE [UNIQUE] INDEX [IF NOT EXISTS] [schema.]name ON table
  ( indexed-column [, ...] ) [WHERE expr]
indexed-column ::= (column-name | expr) [COLLATE name] [ASC|DESC]
#+end_example
- UNIQUE: duplicates rejected (=SQLITE_CONSTRAINT_UNIQUE=); NULLs are all distinct.
- Expression indexes (≥ 3.9.0): expressions may reference only columns of the indexed
  table, no subqueries, only deterministic functions.
- Partial index (=WHERE=): the expression may not contain bound parameters =(local)=
  (=create index ... where x > ?= → =SQLITE_ERROR=), so the DSL renders index predicates in
  inline-literal mode (§6.3.9).
- =NULLS FIRST/LAST= is *not* supported in indexes (NULLs sort first in ASC).
- =COLLATE= per indexed column; default is the column's collation from CREATE TABLE.
- =DROP INDEX [IF EXISTS] name=.
- Introspection: =PRAGMA index_list(table)= → =seq name unique origin(c|u|pk) partial=;
  =PRAGMA index_xinfo(index)= → =seqno cid(-1 rowid, -2 expression) name desc coll key=
  (=(local)= shapes confirmed).

** 3.11 CREATE VIEW (docs lang_createview)
#+begin_example
CREATE [TEMP] VIEW [IF NOT EXISTS] [schema.]name [(column-name, ...)] AS select-stmt
DROP VIEW [IF EXISTS] name
#+end_example
- Read-only (INSTEAD OF triggers for writes). Column-name list (≥ 3.9.0) is recommended;
  otherwise result columns should carry =AS= aliases because auto-generated names are
  not part of the interface.
- The defining SELECT cannot contain bound parameters =(local)= (=create view ... where
  x = ?= → =SQLITE_ERROR "parameters prohibited in views"=), so the DSL renders the view's
  =:as= query in inline-literal mode (§6.3.9).

** 3.12 CREATE TRIGGER (minimal, for orientation) (docs lang_createtrigger)
#+begin_example
CREATE [TEMP] TRIGGER [IF NOT EXISTS] name [BEFORE|AFTER|INSTEAD OF]
  (DELETE | INSERT | UPDATE [OF col, ...]) ON table [FOR EACH ROW] [WHEN expr]
  BEGIN stmt; [stmt;]* END
#+end_example
- Row triggers only; =NEW.col= / =OLD.col=; =RAISE(ABORT|FAIL|ROLLBACK|IGNORE, msg)=;
  BEFORE is the default when neither keyword is given; unknown columns in =UPDATE OF=
  are silently ignored; triggers are dropped with their table. =WITH= and =RETURNING= are
  not allowed inside trigger bodies.
- Scope: the DSL offers =:create-trigger= only as a thin wrapper whose body statements are
  DSL maps rendered in inline-literal mode, or a =:raw= string. It is optional
  (uncertainty §8.7).

** 3.13 ALTER TABLE (docs lang_altertable)
| Form                                   | Since  | Restrictions                                                                                                                                                                                                  |
|----------------------------------------+--------+---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| =ALTER TABLE t RENAME TO new=          | old    | rewrites references in triggers/views (≥ 3.25.0) and FOREIGN KEY clauses (≥ 3.26.0 always; earlier only with foreign_keys=ON); same database only                                                             |
| =ALTER TABLE t RENAME COLUMN a TO b=   | 3.25.0 | also rewrites indexes/triggers/views; fails if it would make a trigger/view ambiguous                                                                                                                         |
| =ALTER TABLE t ADD COLUMN column-def=  | old    | appended last; no PRIMARY KEY / UNIQUE; DEFAULT may not be CURRENT_TIME/DATE/TIMESTAMP or a parenthesised expression; NOT NULL requires a non-NULL default; REFERENCES (with FK on) requires DEFAULT NULL; no STORED generated column; added CHECK / NOT NULL generated constraints are tested against existing rows (≥ 3.37.0) |
| =ALTER TABLE t DROP COLUMN c=          | 3.35.0 | rewrites the table; fails if the column is (part of) a PRIMARY KEY, UNIQUE, indexed, named in a partial-index WHERE, a table CHECK, a foreign key, a generated column expression, a trigger or a view          |
| =ALTER TABLE t ALTER c SET/DROP NOT NULL= | 3.53.0 (2026-04-09) | only NOT NULL can be altered; =(local)= works on better-sqlite3 13.0.3 (SQLite 3.53.4); node:sqlite on Node 22.23.2 bundles 3.51.3 → not available there (§8.1)                                     |
| anything else (change type, drop PK, add constraint) | — | the documented 12-step table-rebuild procedure inside a transaction: create new table, copy, drop old, rename, recreate indexes/triggers/views, =PRAGMA foreign_key_check=; =PRAGMA foreign_keys=OFF= *before* the transaction |
- ALTER TABLE only edits the schema text and re-parses it; RENAME/ADD COLUMN are O(1) in
  table size, DROP COLUMN and constraint-tested ADD COLUMN are O(rows).
- DDL is transactional: =(local)= =BEGIN; CREATE TABLE ...; ROLLBACK= leaves no table,
  and the sqlite.org rebuild procedure itself runs inside BEGIN..COMMIT.

** 3.14 DROP (docs lang_droptable; docs lang_dropindex; docs lang_dropview)
- =DROP TABLE [IF EXISTS] [schema.]name= — removes the table, its indexes and triggers;
  with foreign keys ON it is an implicit DELETE first (FK actions fire, immediate
  violations abort the drop, deferred ones surface at COMMIT).
- =DROP INDEX [IF EXISTS] name=, =DROP VIEW [IF EXISTS] name=, =DROP TRIGGER [IF EXISTS] name=.
- =IF EXISTS= makes the statement a no-op instead of =SQLITE_ERROR "no such table"=.

** 3.15 Conflict resolution (docs lang_conflict)
| Algorithm  | Effect on the statement                                                                                    | Transaction                                     |
|------------+------------------------------------------------------------------------------------------------------------+-------------------------------------------------|
| ROLLBACK   | statement aborts with =SQLITE_CONSTRAINT=                                                                   | whole transaction rolled back                   |
| ABORT      | statement aborts with =SQLITE_CONSTRAINT=, its own changes undone (*default*, SQL-standard behaviour)       | stays open, earlier statements preserved        |
| FAIL       | statement aborts but rows already changed by it are kept                                                   | stays open                                      |
| IGNORE     | offending row skipped, no error (uniqueness / NOT NULL / CHECK only; FK → ABORT)                           | stays open                                      |
| REPLACE    | UNIQUE/PK violation: delete the pre-existing rows then insert/update; NOT NULL: substitute the DEFAULT (else ABORT); CHECK/FK → ABORT; delete triggers fire only with recursive_triggers; change counter not incremented | stays open |
- Given per constraint in CREATE TABLE (=ON CONFLICT x=) or per statement (=INSERT OR x=,
  =UPDATE OR x=); the statement-level =OR= overrides the schema-level clause.
- =REPLACE INTO= is an alias of =INSERT OR REPLACE=; it *deletes* the old row (new rowid,
  FK cascades, lost columns) — prefer UPSERT (§5.2) for "insert or update".

* 5. DML surface for the DSL
** 5.1 INSERT (docs lang_insert)
#+begin_example
[WITH ...] (INSERT | REPLACE | INSERT OR (ROLLBACK|ABORT|FAIL|IGNORE|REPLACE)) INTO [schema.]table [AS alias] [(cols)]
  ( VALUES (expr, ...) [, (expr, ...)]* [upsert-clause]
  | select-stmt [upsert-clause]
  | DEFAULT VALUES )
  [RETURNING ...]
#+end_example
- Multi-row =VALUES= is one statement; there is *no* =DEFAULT= keyword inside VALUES
  (omitted columns get their default, so all rows must list the same columns — the DSL
  enforces equal key sets, §6.3.5).
- =INSERT ... SELECT= with an upsert clause needs a =WHERE= (even =WHERE true=) to avoid
  the =ON= ambiguity; =DEFAULT VALUES= cannot take an upsert clause; the =AS alias= is
  usable in the upsert's SET/WHERE.
- Row count: one statement is limited only by =SQLITE_MAX_VARIABLE_NUMBER= (32766 bound
  values, §5.9) — the DSL chunks =:values= into ≤ 32766/columns rows per statement
  inside one transaction when asked (=core/insert-many!=, §8.14).

** 5.2 UPSERT (docs lang_upsert) (≥ 3.24.0; multiple clauses / target-less DO UPDATE ≥ 3.35.0)
#+begin_example
ON CONFLICT [( indexed-column, ... ) [WHERE expr]] DO ( NOTHING | UPDATE SET col = expr [, ...] [WHERE expr] )
#+end_example
- The conflict target names a UNIQUE/PRIMARY KEY constraint or unique index (partial
  unique indexes need the matching =WHERE=); it may be omitted only on the *last* clause.
- Only uniqueness constraints trigger it (not NOT NULL / CHECK / FK); the decision is per
  row; the first matching clause wins.
- In =DO UPDATE=, bare column names are the *existing* row, =excluded.col= is the row that
  would have been inserted; the trailing =WHERE= turns the update into a no-op.
- The DO UPDATE runs as =OR ABORT= regardless of any other conflict clause; virtual tables
  unsupported.
- =(local)= =INSERT ... ON CONFLICT(a) DO UPDATE SET b = excluded.b RETURNING a, b= returns
  the updated row.

** 5.3 RETURNING (docs lang_returning) (≥ 3.35.0)
- =RETURNING expr [AS alias], ... | *= on top-level INSERT/UPDATE/DELETE (not inside
  triggers, not as a subquery/CTE source).
- INSERT/UPDATE see post-change values, DELETE pre-delete values; rows *directly*
  modified only (no FK-action/trigger side effects); an UPSERT reports inserted *and*
  updated rows.
- Output order is arbitrary and unrelated to processing order; all changes happen on the
  first step and the output is buffered in memory (large RETURNING sets cost RAM).
- No aggregates/window functions at top level; only the target table may be referenced
  (not =UPDATE FROM= auxiliaries); values are pre-AFTER-trigger.
- Driver: a RETURNING statement is a =reader= (=(local)= =st.reader= true) → use
  =all()/get()=, not =run()=; =lastInsertRowid= is unaffected for WITHOUT ROWID tables, so
  =RETURNING= is the portable way to get generated keys.

** 5.4 SELECT (docs lang_select; docs lang_with; docs windowfunctions)
| Piece              | SQLite specifics                                                                                                                                          |
|--------------------+-----------------------------------------------------------------------------------------------------------------------------------------------------------|
| result columns     | =expr [AS alias]=, =*=, =table.*=; aliases usable in ORDER BY/GROUP BY/HAVING                                                                             |
| FROM               | tables, subqueries, =table-valued functions= (=json_each=, =json_tree=), comma joins                                                                      |
| JOIN               | =[NATURAL] [LEFT|RIGHT|FULL] [OUTER] | INNER | CROSS JOIN= with =ON= / =USING=; RIGHT/FULL since 3.39.0 (=(local)= works); ON/USING may be omitted (becomes unconstrained) — the DSL always requires one except for CROSS |
| WHERE / GROUP BY / HAVING | bare columns allowed in aggregate queries (quirks §6) — the DSL does not check         |
| window functions   | =fn(args) [FILTER (WHERE ..)] OVER (name | ([PARTITION BY ..] [ORDER BY ..] [frame]))=, =WINDOW name AS (...)=; 11 built-ins (=row_number rank dense_rank percent_rank cume_dist ntile lag lead first_value last_value nth_value=) + any aggregate; since 3.25.0 |
| ORDER BY           | =expr [COLLATE c] [ASC|DESC] [NULLS FIRST|LAST]= (NULLS FIRST/LAST since 3.30.0, =(local)= works); NULLs sort first by default                             |
| LIMIT / OFFSET     | expressions must be integers (bound parameters fine); negative LIMIT = no limit; the =LIMIT x, y= comma form is *offset first* — the DSL never emits it   |
| compound           | =UNION | UNION ALL | INTERSECT | EXCEPT=; ORDER BY/LIMIT only at the end and apply to the whole compound                                                  |
| WITH               | =WITH [RECURSIVE] name [(cols)] AS [NOT] MATERIALIZED (select), ...= at the top of SELECT/INSERT/UPDATE/DELETE (not inside triggers; not before later members of a compound); MATERIALIZED hints ≥ 3.35.0 |
| VALUES             | =VALUES (..), (..)= is a select-stmt (usable in CTEs and compounds)                                                                                       |
| operators of note  | =IS [NOT]=, =IS [NOT] DISTINCT FROM= (≥ 3.39.0), =LIKE= (case-insensitive ASCII), =GLOB= (case-sensitive), =REGEXP= (needs a UDF), =->= / =->>= JSON (≥ 3.38.0), =||= concat, =BETWEEN=, =IN (list | subquery)=, =EXISTS=, =CAST=, =CASE=, =COLLATE= |

** 5.5 UPDATE / DELETE (docs lang_update; docs lang_delete)
- =UPDATE [OR conflict] table [AS alias] SET col = expr | (c1, c2) = (expr...) [FROM ...] [WHERE ...] [RETURNING ...]=;
  =UPDATE FROM= (≥ 3.33.0, PostgreSQL style; the target is not repeated in FROM; a
  multi-match join picks an arbitrary row).
- =DELETE FROM table [WHERE ...] [RETURNING ...]=; a WHERE-less DELETE uses the truncate
  optimisation (no row-level triggers/FK checks skipped, only speed).
- =ORDER BY ... LIMIT ... [OFFSET]= on UPDATE/DELETE only with
  =SQLITE_ENABLE_UPDATE_DELETE_LIMIT= (better-sqlite3 yes, node:sqlite no); ORDER BY only
  selects which rows fall inside the LIMIT, not the deletion order or RETURNING order.
  =(local)= the clause order is =... WHERE .. RETURNING .. ORDER BY .. LIMIT ..=: putting
  RETURNING after LIMIT is a syntax error. The renderer emits that order.

** 5.6 Parameter binding forms (SQLite side) (docs lang_expr §4; docs c3ref bind_blob)
| Form    | SQLite meaning                                                                                                              | Driver support                                                         |
|---------+-----------------------------------------------------------------------------------------------------------------------------+------------------------------------------------------------------------|
| =?=     | next index (largest so far + 1); "discouraged" by sqlite.org because miscounting is easy — irrelevant for a renderer that emits them | both drivers                                                     |
| =?NNN=  | explicit index NNN ≤ =SQLITE_MAX_VARIABLE_NUMBER=; the same NNN may repeat                                                  | node:sqlite yes; better-sqlite3 *no* (§2.3)                            |
| =:AAAA= =@AAAA= =$AAAA= | named; also numbered (next index); =$= form allows Tcl-style =::= and =(...)= suffixes                              | both; better-sqlite3 keys are bare names                               |
| unbound | a parameter that is never bound reads as NULL                                                                               | better-sqlite3 throws on count mismatch; =exec= cannot bind at all     |
House position (§7.7): the renderer emits only anonymous =?= in left-to-right order and
returns =:params= as a vector; named parameters are not part of the DSL (no name-collision
rules to explain, works on both drivers).

** 5.7 Value binding rules: CLJS value → driver value → SQLite storage
| CLJS value                                  | =driver/->param= result                | SQLite type / note                                                                                                               |
|---------------------------------------------+----------------------------------------+----------------------------------------------------------------------------------------------------------------------------------|
| =nil=                                       | =null=                                 | NULL                                                                                                                             |
| integer number (=(integer? x)=, safe, i.e. ≤ 2^53−1 in magnitude) | =js/BigInt x=            | INTEGER — because a JS number would bind as REAL (§2.3) and land as ='5.0'= in TEXT columns / REAL in =ANY= columns              |
| non-integer finite number                   | as is                                  | REAL                                                                                                                             |
| number with magnitude > 2^53−1              | argument-error (=:reason :unsafe-integer=) | caller must pass a BigInt (exact) — silently binding a rounded double is the kind of bug this rule exists for                 |
| =NaN=, =±Infinity=                          | argument-error                         | SQLite would store NULL / Infinity silently                                                                                      |
| BigInt                                      | as is                                  | INTEGER (int64 range, else driver RangeError → argument-error)                                                                   |
| string                                      | as is; NUL inside → argument-error     | TEXT                                                                                                                             |
| =true= / =false=                            | =1n= / =0n=                            | INTEGER 1/0 (house position §7.1)                                                                                                |
| Buffer / Uint8Array / ArrayBuffer view      | as is (ArrayBuffer wrapped)            | BLOB                                                                                                                             |
| keyword                                     | *dsl-error in value position*          | keywords are identifiers; use a string for an enum-like value                                                                    |
| js/Date                                     | argument-error (=:reason :date=)       | caller converts: =(.getTime d)= for epoch ms INTEGER (house default §7.4) or =(.toISOString d)= for TEXT                          |
| vector / map / set / seq                    | dsl-error unless wrapped =[:param v]=; =[:param v]= → argument-error unless v is one of the bindable types above | a CLJS collection is never auto-serialised; JSON is the caller's job (=js/JSON.stringify= of =clj->js=), stored as TEXT |
| JS object                                   | argument-error                         |                                                                                                                                  |
Reading back (=util/row->clj=): keys kebab-cased, values untouched — INTEGER → number
(BigInt when =:safe-integers? true=), REAL → number, TEXT → string, BLOB → Buffer, NULL →
nil. Booleans and dates are *not* reconstructed (no schema knowledge at read time; §8.4).

** 5.8 Identifier quoting rules (docs lang_keywords; docs quirks §8-9; docs bs3 SQLITE_DQS=0)
- SQLite accepts ="x"= (standard), =[x]= (MS), =`x`= (MySQL) as identifier quotes; the
  library uses *only* double quotes. Inside, a double quote is written as two (="a""b"=)
  — the same rule as single quotes in string literals.
- With the driver's =SQLITE_DQS=0= a double-quoted token that is not an identifier is an
  error instead of a string literal (§2.8), so a mistyped column name fails loudly.
- Any keyword becomes a legal name once quoted (="select"=); SQLite also lets many
  keywords be bare identifiers, but the library never relies on that (147 keywords, list
  grows).
- Names are case-insensitive for matching but case-preserving in the schema (=CREATE
  TABLE "Users"= can later be referenced as =users=); kebab keywords always render lower
  snake_case; string identifiers are passed through exactly (=util/ident-name=).
- Schema-qualified names (=main.t=, =temp.t=, attached =aux.t=) quote each part.
- A NUL byte inside an identifier is rejected before rendering (=util/ident-name=): the C
  string SQLite receives would be truncated, which is an injection vector.
- Function names in =[:fn ...]= forms are rendered unquoted (SQLite function names are
  never quoted) and therefore restricted to =[a-z_][a-z0-9_]*= (§6.3.7).

* 6. honeysql comparison and the sqlite-cljs DSL
** 6.1 What honeysql gets right (docs honeysql) (2.7.x, README/getting-started/clause-reference read 2026-09-25)
- SQL statements are plain hash maps keyed by clause (=:select :from :where ...=), SQL
  expressions are vectors with the operator/function first (=[:= :id 1]=,
  =[:count :*]=). Everything composes with =assoc=/=merge=/=update=; no builder objects.
- Keywords/symbols are SQL entities, *strings are values* that become parameters. This
  single rule is what makes the data safe: =[:= :name "x"]= → =name = ?= with ="x"= bound.
- Namespaced keywords are table-qualified columns (=:users/id= → =users.id=), aliases are
  pairs (=[:name :item]=, =[[:users :u]]=), =:order-by= takes =[expr :desc]= pairs,
  =:where= nests =[:and ...]= / =[:or ...]=, =nil= renders =IS NULL=.
- =format= returns =["SQL" param ...]=; =:params= + =:?name= / =[:param :x]= give named
  parameters; =:inline true= exists for copy/paste use only.
- Identifier quoting is off by default and only "unusual" entities are auto-quoted (since
  2.3.928); the docs say "if the table, column, or function names could be provided by
  an external source, you should specify =:quoted true=".
- DDL: =:create-table= + =:with-columns= (vector of =[name type & descriptors]=,
  everything inlined), =:alter-table= with =:add-column :drop-column :rename-column=,
  =:create-index=, =:create-view=, =:drop-table=; =:on-conflict= / =:do-update-set= /
  =:do-nothing= (PostgreSQL-style, so SQLite compatible), =:returning=,
  =:replace-into= ("only supported by MySQL and SQLite"), =:with= CTEs, window clauses,
  =:raw=, =:lift= (force a value), =:nest=.
- Escape hatches are explicit: =[:raw "..."]= for literal SQL, =[:lift v]= to force a
  value, =[:inline v]= to force a literal.

** 6.2 Copy / drop table
| honeysql behaviour                                       | sqlite-cljs decision                                                                                                          |
|----------------------------------------------------------+-------------------------------------------------------------------------------------------------------------------------------|
| maps = statements, vectors = expressions, keywords = entities, strings = values | *copy verbatim* — this is the whole design                                                             |
| =:from [:users]= (vector) and =:from :users= both accepted | copy (accept keyword or vector; alias pairs)                                                                                  |
| =[:= :x nil]= → =IS NULL=, =[:<> :x nil]= → =IS NOT NULL=  | copy                                                                                                                          |
| =:where [:and ...]= / =[:or ...]= / =[:not ...]=, =[:in :x [1 2]]=, =[:between :x 1 2]=, =[:like ...]=, =[:exists {..}]= | copy; add =[:glob]=, =[:is]=, =[:is-not]=, =[:is-distinct-from]=, =[:->> ...]=, =[:collate expr :nocase]= |
| alias pairs =[expr :alias]= inside =:select=              | copy                                                                                                                          |
| namespaced keyword = table.column                        | copy (=:users/id=), also =:users.id=                                                                                          |
| =format= → =["sql" & params]= vector                      | *drop*: render returns a kebab map ={:sql "..." :params [...]}= (house rule: maps in/out); no positional vector convention     |
| quoting off / auto-quote "unusual" names                 | *drop*: every identifier is always quoted with ="..."= (§5.8); there is no unquoted mode                                      |
| =:inline= (any value as literal)                          | *drop* for queries; DDL uses a restricted literal renderer internally (§6.3.9); user data can never be inlined                |

| =:on-conflict {:on-constraint :name}=                     | *drop* — SQLite has no named conflict targets; targets are column lists (+ optional =:where= for partial unique indexes)      |

** 6.3 Proposed DSL syntax (exact shapes; the renderer implements these and rejects anything else with =:sqlite-cljs/dsl-error=)
Conventions: keywords are identifiers and are rendered kebab→snake and quoted
(=:created-at= → ="created_at"=); strings in *expression positions* are values (bound);
strings in *identifier positions* (table/column names) are exact names, quoted verbatim;
=nil= is =NULL=; booleans are the integers 1/0 (§7.1); vectors starting with a keyword are
operator/function calls; maps in expression positions are subqueries.

*** 6.3.1 Table definition
#+begin_src clojure
{:create-table :users
 :if-not-exists? true                      ; optional, DEFAULT TRUE (idempotent migrate!)
 :strict? true                             ; optional, DEFAULT TRUE (house position §7.1)
 :without-rowid? false                     ; optional, default false; requires a primary key
 :temp? false                              ; optional
 :columns                                  ; VECTOR (ordered) of [name type opts?]
 [[:id :integer {:primary-key? true}]                     ; INTEGER PRIMARY KEY (rowid alias)
  [:email :text {:not-null? true :unique? true :collate :nocase}]
  [:name :text {:not-null? true}]
  [:age :integer {:check [:>= :age 0]}]
  [:active :integer {:not-null? true :default true}]      ; DEFAULT 1 (booleans are 0/1)
  [:org-id :integer {:references {:table :orgs :column :id :on-delete :cascade :on-update :restrict
                                  :deferrable :initially-deferred}}]   ; or :deferrable true / false
  [:created-at :integer {:not-null? true :default [:raw "(unixepoch('subsec') * 1000)"]}]
  [:updated-at :text {:default :current-timestamp}]       ; allow-listed keyword literal
  [:data :text {:default "{}"}]                           ; string literal → DEFAULT '{}'
  [:label :text {:generated-as {:expr [:|| :name " <" :email ">"] :stored? true}}]  ; GENERATED ALWAYS AS (...) STORED
  [:legacy :any {}]]
 :primary-key [:a :b]                      ; optional composite PK (only when no column has :primary-key?)
 :unique [[:org-id :email] [:name]]        ; optional table UNIQUE constraints
 :check [[:or [:= :active 0] [:= :active 1]]]
 :foreign-keys [{:columns [:org-id] :table :orgs :ref-columns [:id] :on-delete :cascade :name :fk-org}]
 :constraints                              ; optional, the vector form (same constraints, with opts)
 [[:unique [:name] {:on-conflict :ignore}]
  [:check [:> :age 0] {:name :ck-age}]
  [:foreign-key [:org-id] [:orgs :id] {:on-delete :cascade}]
  [:primary-key [:a :b] {:name :pk-ab}]]
 :indexes                                  ; optional; rendered as separate CREATE INDEX statements
 [[:users-email-idx [:email] {:unique? true}]
  [nil [:org-id [:created-at :desc]] {:where [:= :active 1]}]]}   ; nil name → users_org_id_created_at_idx
#+end_src
Column =opts= keys (all optional; canonical spelling): =:primary-key? true|:asc|:desc=,
=:autoincrement? true= (only with =:primary-key?= on =:integer=, never in WITHOUT ROWID;
rendered only on request per §3.6), =:not-null? true=, =:unique? true=, =:check expr=,
=:default literal|keyword|[:raw ..]|expr=, =:collate :binary|:nocase|:rtrim|"name"=,
=:references {:table t :column c :on-delete a :on-update a :deferrable d}= (actions ∈
=#{:no-action :restrict :set-null :set-default :cascade}=, deferrable ∈ =true|false|
:initially-deferred|:initially-immediate=), =:generated-as {:expr e :stored? bool}=,
=:on-conflict= (conflict clause for PK/NOT NULL/UNIQUE ∈ =#{:rollback :abort :fail :ignore
:replace}=), =:name= (CONSTRAINT name). The bare spellings =:primary-key :not-null :unique
:autoincrement=, =:references [table col]= with =:on-delete=/=:on-update= beside it, and
=:generated expr= + =:stored= are accepted as aliases. Types: =:integer :int :real :text
:blob :any= plus =:numeric= and =[:raw "VARCHAR(255)"]= only with =:strict? false= — anything
else (=:boolean=, =:datetime=, =:varchar= ...) is an =:sqlite-cljs/argument-error= naming the
=:column= (§3.2, task directive).

Renders (with =:strict? true=) to:
#+begin_example
CREATE TABLE IF NOT EXISTS "users" (
  "id" INTEGER PRIMARY KEY,
  "email" TEXT NOT NULL UNIQUE COLLATE NOCASE,
  ...
  "org_id" INTEGER REFERENCES "orgs"("id") ON DELETE CASCADE ON UPDATE RESTRICT DEFERRABLE INITIALLY DEFERRED,
  "created_at" INTEGER NOT NULL DEFAULT (unixepoch('subsec') * 1000),
  "label" TEXT GENERATED ALWAYS AS ("name" || ' <' || "email" || '>') STORED,
  UNIQUE ("org_id", "email"),
  ...
) STRICT
#+end_example
followed by =CREATE UNIQUE INDEX IF NOT EXISTS "users_email_idx" ON "users" ("email")= etc.
=ddl/render= returns ={:statements ["CREATE TABLE ..." "CREATE UNIQUE INDEX ..."]}= (one SQL
string per statement, never parameters) because =prepare= accepts one statement at a time
(§2.2); =query/execute-all!= / =query/exec!= / =migrate!= run them in one transaction.

*** 6.3.2 Indexes and views
#+begin_src clojure
{:create-index :users-org-created-idx     ; nil → users_org_id_created_at_idx
 :on :users
 :columns [:org-id [:created-at :desc] [[:lower :email] :asc [:collate :nocase]]]  ; column | [col :desc] | [expr flags..]
 :unique? true :if-not-exists? true        ; :if-not-exists? defaults to true
 :where [:= :active 1]}                    ; partial index; literal mode (no parameters allowed, §3.10)
;; renders CREATE UNIQUE INDEX IF NOT EXISTS "users_org_created_idx" ON "users" ("org_id", "created_at" DESC, lower("email") COLLATE NOCASE ASC) WHERE "active" = 1

{:create-view :active-users
 :if-not-exists? true :temp? false
 :columns [:id :name]                      ; recommended by sqlite.org (§3.11)
 :as {:select [:id :name] :from :users :where [:= :active 1]}}   ; rendered in literal mode (§3.11)
#+end_src

#+begin_src clojure
{:alter-table :users :rename-to :people}

{:alter-table :users :drop-column :legacy}
{:alter-table :users :alter-column [:name :set-not-null]}     ; SQLite ≥ 3.53 only (§3.13), else dsl-error from the version check

{:drop-index :users-email-idx}
{:drop-view :active-users}

*** 6.3.4 SELECT
#+begin_src clojure
{:with [[:recent {:select [:id] :from :orders :where [:> :created-at 1700000000000]}]
        [[:tree [:id :parent-id]] {:union-all [...]} {:recursive true}]]   ; optional CTEs
 :select [:id :name [:email :contact] [[:count :*] :n] [[:lower :name] :lname] :o/name]   ; [x y] is ALWAYS x AS y; wrap bare calls [[:lower :name]] or use [:as expr :alias]

              [:in :id [1 2 3]]                              ; IN (?, ?, ?) — empty vector renders 0=1 (§7.8)

              [:is :deleted-at nil]                          ; same as [:= :deleted-at nil]

SELECT "id", "name", "email" AS "contact", count(*) AS "n", lower("name") AS "lname", "o"."name" FROM "users" INNER JOIN "orgs" AS "o" ON "o"."id" = "u"."org_id" LEFT JOIN "profiles" AS "p" USING ("user_id") WHERE ("active" = ? AND "id" IN (?, ?, ?) AND ...) GROUP BY "org_id" HAVING count(*) > ? ORDER BY "name" DESC, "id", lower("email") ASC NULLS LAST LIMIT ? OFFSET ?= with =:params [1 1 2 3 "a%" 18 "admin" 1 10 20]=.

Compound selects: ={:union [{..} {..}]}=, =:union-all=, =:intersect=, =:except= (+ outer
=:order-by=/=:limit=).

*** 6.3.5 INSERT and UPSERT
#+begin_src clojure
{:insert-into :users :values [{:name "a" :email "a@x"} {:name "b" :email "b@x"}]}
;; all maps must have the same key set (else argument-error): SQLite VALUES has no DEFAULT keyword
{:insert-into :users :columns [:name :email] :values [["a" "a@x"] ["b" "b@x"]]}
{:insert-into :users :columns [:name] :select {:select [:name] :from :staging :where [:= 1 1]}}
;; the renderer appends WHERE true to a parameter-less select when an upsert clause follows (parsing ambiguity, §5.2)
{:insert-into :users :or :ignore :values [...]}                       ; INSERT OR IGNORE|REPLACE|ABORT|FAIL|ROLLBACK
{:insert-into :users :default-values true}
{:insert-into :users :values [{:email "a@x" :name "A" :count 1}]
 :on-conflict [:email]                                               ; conflict target (column list); [] or omitted → no target
 :do-update-set [:name]                                               ; SET "name" = excluded."name"
 :where [:> :excluded/updated-at :users/updated-at]}                  ; optional DO UPDATE ... WHERE
{:insert-into :users :values [{...}]
 :on-conflict [:email] :do-update-set {:count [:+ :users/count 1] :name :excluded/name}}
{:insert-into :users :values [{...}] :on-conflict [] :do-nothing true} ; ON CONFLICT DO NOTHING
{:insert-into :users :values [{...}]
 :on-conflict [[[:email] {:do-update-set [:name]}] [[] {:do-nothing true}]]}   ; multiple ON CONFLICT clauses: vector of [target clause-map] pairs (≥ 3.35); clause maps take :do-update-set / :do-nothing / :where (target predicate) / :update-where
{:insert-into :users :values [{...}] :returning [:id :created-at]}    ; or :returning :*
#+end_src
=:on-conflict= may carry a partial-index predicate as a single pair:
=:on-conflict [[:email] {:where [:= :active 1]}] :do-update-set [:name]= (the DO clause then
comes from the top-level keys). Bulk =:values= above 32766 parameters are split by
=dsl/render-chunked= and =query/execute!= runs the chunks in one transaction (§8.14).

*** 6.3.8 Render output and execution
- =dsl/render= → ={:sql "..." :params [...]}= (params in ? order as ClojureScript values;
  =core/->param= converts them at bind time). Pure, no I/O, fully unit-testable without a
  database. =dsl/render-chunked= → vector of statements for bulk inserts.
- =ddl/render= → ={:statements ["..." ...]}= (never any params, §6.3.9).
- =query/query-all!= (rows), =query/query-one!= (first row or nil), =query/query-value!=
  (first column), =query/execute!= (={:changes n :last-insert-rowid n}= or RETURNING rows),
  =query/execute-all!=, =query/exec!=, =query/transact!= accept a DSL map, ={:sql .. :params ..}=,
  =[sql & params]= or a plain SQL string (§9).

*** 6.3.9 Literal mode (DDL only)
CHECK, DEFAULT, generated-column expressions, partial-index predicates and view bodies
cannot contain bound parameters (=(local)= §3.4, §3.10, §3.11). The renderer therefore has
two modes: =:params= (queries; every value → =?=) and =:literal= (DDL; values inlined). In
literal mode only these value shapes are accepted: integers and finite floats (rendered
with =str=, no exponent for integers), strings (single-quoted with ='= doubled, NUL
rejected), =nil= → =NULL=, booleans → =1=/=0=, and the allow-listed keywords
=:current-time :current-date :current-timestamp :null :true :false=. Blobs, BigInt beyond
2^53, Dates, NaN/Infinity and any other type are dsl-errors. DDL comes from source code,
not from users, but the same escaping discipline applies.

** 6.4 migrate! design (idempotent apply)
The runner is an idempotent "bring the database up to these definitions" apply, not a
versioned up/down runner. The original up/down proposal is kept at the end of this
section for the record.
#+begin_src clojure
(migrate/migrate! db
  [{:create-table :orgs ...}
   {:create-table :users ... :indexes [...]}
   {:create-index :users-email-idx :on :users :columns [:email] :unique? true}
   {:create-view :user-emails :columns [:email] :as {:select [:email] :from :users}}
   {:alter-table :users :add-column [:nickname :text {:default "" :not-null? true}]}]
  {:allow-newer? false :log println})
;; => {:created [:orgs :users :users-org-idx :users-email-idx :user-emails] :existing [] :altered [:users]
;;     :dropped [] :user-version 5 :previous-user-version 0 :sqlite-version "3.53.4"}
#+end_src
Algorithm (implemented in =sqlite-cljs.migrate=):
1. Validate: a vector of DDL definition maps that each render (=migrate/validate= is pure);
   otherwise migration-error =:reason :invalid-defs=.
2. Read =PRAGMA user_version=. If it is above =(count defs)= the code is older than the
   database → migration-error =:reason :database-newer= unless =:allow-newer? true=.
3. In ONE =BEGIN IMMEDIATE= transaction, for each def in order:
   - =:create-table= — absent: create it and its =:indexes=; present: leave it, create its
     indexes when absent.
   - =:create-index= / =:create-view= / =:create-trigger= — create when absent (by name in
     =sqlite_master=), else report =:existing=.
   - =:alter-table= — apply only when its effect is not yet there (add-column when the
     column is missing, rename-column / rename-to when the old name exists and the new one
     does not, drop-column when the column exists, alter-column always); a =:rename-to= whose
     source is absent is skipped (a fresh database creates the renamed table directly).
   - =:drop-*= — apply when the object exists.
   - a statement SQLite refuses → migration-error =:reason :statement-failed :index :def
     :code :cause=.
4. Verify: every =:create-table= def must now exist with all declared columns and declared
   types (=PRAGMA table_xinfo=; extra columns are fine). Otherwise migration-error
   =:reason :drift :table :missing :type-mismatch= — nothing is altered automatically.
5. =PRAGMA user_version = (count defs)= (fingerprint, not a cursor), COMMIT, clear the
   statement cache. Any throw rolls everything back (DDL is transactional, §3.13).
Evolving a table: the table def describes the DESIRED shape, explicit =:alter-table= defs
bring existing databases there, renames precede the renamed def (see the namespace
docstring example). =migrate/status!= → ={:user-version :schema-version :tables :views
:indexes :triggers}=.

*** Original proposal (not implemented; versioned up/down runner)
#+begin_src clojure
(migrate/migrate! db
  [{:version 1 :name "init"
    :up [{:create-table :orgs ...} {:create-table :users ...}]}
   {:version 2 :name "users.nickname"
    :up [{:alter-table :users :add-column [:nickname :text {}]}
         "UPDATE users SET nickname = name"]                 ; raw SQL strings allowed
    :down [{:alter-table :users :drop-column :nickname}]}]
  {:target 2 :dry-run? false :log println})
#+end_src
Steps: validate versions (positive, increasing, gap-free); =current = user_version=; apply
each pending migration in its own =BEGIN IMMEDIATE= and set =user_version= inside it; toggle
=foreign_keys= outside transactions when a migration asks (§3.7); optional =:down= steps.
=ddl/introspect= / =ddl/diff= / =ensure-schema!= from that sketch became the
=table_xinfo=-based verification step above.

* 7. Pitfalls and house positions
Each item states the pitfall, the evidence, and the position sqlite-cljs takes.

** 7.1 Booleans and STRICT by default
Pitfall: no BOOLEAN storage class; =BOOLEAN= as a declared type is NUMERIC affinity in a
non-strict table and *illegal* in a STRICT table (§3.2, §3.3). Position: booleans bind
as INTEGER 1/0 (§5.7); the DSL type vocabulary has no =:boolean= (columns are
=:integer= with an optional =:check [:in :col [0 1]]=); tables are =STRICT= by default so
type mistakes fail at write time instead of hiding as text.

** 7.2 AUTOINCREMENT
Pitfall: cargo-culted from MySQL; sqlite.org says it should be avoided (§3.6). Position:
=INTEGER PRIMARY KEY= (rowid alias) is the idiom; =:autoincrement true= is rendered only
when asked and =ddl/lint= flags it.

** 7.3 Foreign keys: enforcement and indexes
Pitfall: stock SQLite does not enforce FKs; both drivers do, but the setting is
per-connection and a no-op inside transactions; child keys are not indexed
automatically (§3.7). Position: =core/open!= sets =PRAGMA foreign_keys=ON= explicitly;
=migrate!= toggles it only outside transactions; =ddl/lint= warns on un-indexed child
keys.

** 7.4 Dates
Pitfall: no DATETIME class; =js/Date= binds as NULL silently in node:sqlite and throws in
better-sqlite3 (§2.3, §2.9). Position: the library refuses =js/Date= (argument-error) and
recommends *INTEGER epoch milliseconds* as the house default (sortable, cheap, exact,
what =js/Date= natively holds) with =[:raw "(unixepoch('subsec') * 1000)"]= as the DEFAULT;
ISO-8601 TEXT (="YYYY-MM-DD HH:MM:SS.SSS"=, UTC) is the documented alternative when
SQLite date functions or human readability matter. No automatic reconstruction on read
(§8.4).

** 7.5 Integers: REAL binding and the 2^53 cliff
Pitfall 1: JS numbers bind as REAL in *both* drivers (§2.3) — ='5.0'= ends up in TEXT
columns and REAL in =ANY= columns, and =typeof()= lies. Position: integral safe numbers
are converted to BigInt before binding (§5.7).
Pitfall 2: reading INTEGER beyond ±2^53: better-sqlite3 rounds silently, node:sqlite
throws (§2.3, §2.9). Position: =:safe-integers? false= by default (rowids and counters
are far below 2^53; BigInts are awkward in CLJS arithmetic), documented; =:safe-integers?
true= per connection or =:safe-integers?= per query flips reads to BigInt; the
=lastInsertRowid= follows the same switch.

** 7.6 Concurrency: one connection, serialised, IMMEDIATE transactions
Pitfall: SQLite allows one writer at a time; two connections in one process racing on
=BEGIN IMMEDIATE= produce =SQLITE_BUSY= after =busy_timeout= (=(local)= §2.4); DEFERRED
transactions can fail with BUSY mid-way when upgrading to write (§2.5); the driver is
synchronous so there is no benefit from a pool in one thread. Position: one connection
per database per process (=core/db= returns one); =transact!= defaults to =:immediate= and
rejects nested calls (=:reason :nested-transaction=; the driver's savepoint nesting is
deliberately not exposed); =busy_timeout= 5000 ms default;
multi-process access is supported by WAL + busy timeout, and =busy-error?= lets callers
retry. No pool (uncertainty §8.13 covers worker threads).

** 7.7 Only =?= parameters
Position: the renderer emits anonymous =?= in order; named parameters are not exposed
(better-sqlite3 rejects =?NNN=, prefixes differ between drivers, §5.6).

** 7.8 Empty IN lists and WHERE-less writes
Pitfall: =x IN ()= is a syntax error; =DELETE FROM t= without WHERE deletes everything.
Position: =[:in x []]= renders =0=1= (=:not-in= → =1=1=); =:update=/=:delete-from= without
=:where= is a dsl-error unless =:all? true=.

** 7.9 WAL on network filesystems and WAL growth
Pitfall: WAL "does not work over a network filesystem" (shared memory wal-index) and
=journal_mode = WAL= silently returns the old mode when it cannot switch; long readers
starve checkpoints and the =-wal= file grows (docs wal; docs bs3 performance.md). Position:
=core/open!= checks the returned mode and raises config-error =:reason :wal-unavailable=
unless =:wal? :try=; =core/checkpoint!= exposes =wal_checkpoint(RESTART|TRUNCATE)=; the
README warns against network shares (SQLite's own advice) and =:memory:= databases ignore
WAL (=(local)= returns =memory=).

** 7.10 Durability defaults
Pitfall: with the driver's =SQLITE_DEFAULT_WAL_SYNCHRONOUS=1=, a WAL database opened by a
new connection runs =synchronous=NORMAL= (a power loss can drop the last committed
transactions; the file stays consistent) — and the same file under node:sqlite runs
FULL (§4.1). Position: keep the driver default, expose =:synchronous :full= for callers
who need power-loss durability, document it.

** 7.11 REPLACE INTO is a DELETE
Pitfall: =INSERT OR REPLACE= deletes the conflicting row (new rowid, FK cascades,
columns not listed reset to defaults) (§3.15). Position: the DSL offers =:or :replace= but
the docstring points to =:on-conflict ... :do-update-set= as the "upsert".

** 7.12 Double-quoted string literals
Pitfall: stock SQLite treats ="misspelled"= as a string literal (quirks §8). Position: the
driver compiles =DQS=0= and the library never emits double quotes around values; an
identifier typo therefore fails with =no such column= (=(local)=).

** 7.13 NUL characters
Pitfall: a NUL inside a bound string is stored intact but every SQL string function
treats it as the end of the string (=(local)= =length()= = 1, §2.3; undefined per
sqlite.org), and inside an identifier it would truncate the SQL text. Position:
argument-error for both (identifiers already enforced in =util/ident-name=; values in
=driver/->param=).

** 7.14 CHECK / DEFAULT / view / partial-index expressions are literal SQL
Pitfall: parameters are prohibited in schema expressions (=(local)= §3.4, §3.10, §3.11).
Position: literal mode with a strict literal vocabulary (§6.3.9); user data never reaches
DDL.

** 7.15 =ON CONFLICT= fires only for uniqueness
Pitfall: UPSERT does nothing for NOT NULL/CHECK/FK failures (§5.2); =IGNORE= also treats
FK violations as ABORT (§3.15). Position: documented; =constraint-error?= + =sqlite-code=
let callers branch on the extended code.

** 7.16 =lastInsertRowid= is not a primary key
Pitfall: meaningless for WITHOUT ROWID tables and for non-INTEGER PKs (§3.6). Position:
=execute!= returns it verbatim but the docs steer to =:returning=.

** 7.17 Statement caching vs schema changes
Pitfall: a cached prepared statement survives =ALTER TABLE= (auto-recompile, =(local)=
§2.2) but =columns()= metadata lags until re-execution. Position: the driver's statement
cache is keyed by SQL text and cleared by =migrate!= after each migration (§8.12).

* 8. Uncertainties (numbered; each has a recommended house position)
1. *SQLite version skew between the driver and node:sqlite.* better-sqlite3 13.0.3 bundles
   3.53.4 (=ALTER COLUMN SET NOT NULL= works =(local)=), Node 22.23.2 bundles 3.51.3. A
   future node:sqlite binding must gate features on =sqlite_version()=. Position: =ddl=
   checks the connection's version (=core/sqlite-version=) before rendering =:alter-column=
   and =:->>=-style operators, raising dsl-error with the required version.
2. *Prebuilt binary coverage.* 13.0.3 ships 8 prebuilds (§1.3); Electron and other
   runtimes are "theoretically" supported by N-API (docs bs3 v13.0.0 notes). Untested
   here. Position: document =npm rebuild= / =electron-rebuild=; not a library concern.
3. *node:sqlite promotion on Node 22.* Docs for the 22 line still say Stability 1.1;
   whether the ExperimentalWarning will ever disappear on 22.x is unknown. Position: not
   relevant while better-sqlite3 is the driver; revisit if the house moves to Node ≥ 25.
4. *Reading booleans/dates back.* Without schema knowledge the library cannot turn
   INTEGER 1 into =true= or epoch ms into =js/Date=. Options: (a) leave raw (current
   position), (b) optional per-query =:coerce {:active :boolean :created-at :date}= map,
   (c) derive from =table_xinfo= declared types (only for =:boolean=/=:datetime=-like
   type names, which STRICT forbids). Position: (a) by default; (b) shipped as the explicit
   opt-in per-query =:coerce {:col :boolean|:date|:number|:bigint|:json|:keyword|fn}=
   option of =query/query-all!= etc.
5. *=Infinity= binding.* better-sqlite3 stores REAL Infinity (=(local)=); node:sqlite
   keeps it too; the value is not JSON-serialisable and compares oddly. Position:
   argument-error (§5.7) — confirm no house use case needs ±Infinity.
6. *Non-strict type names.* Whether to allow =[:raw "VARCHAR(255)"]= as a column type for
   legacy schemas (affinity TEXT). Position: allow only via =:raw= and only when
   =:strict? false=, documented as compatibility.
7. *Triggers in the DSL.* The DSL sketch (§3.12) renders trigger bodies in literal mode;
   the value of a data-driven trigger DSL vs. =:raw= strings is unclear. Position:
   =:create-trigger= ships with =:raw= body strings only; revisit on demand.
8. *=application_id=.* Whether =migrate!= should stamp it. Position: optional
   =:application-id= (integer) written on the first migration; never asserted on read.
9. *Window frames.* Frame specifications (=ROWS BETWEEN ...=) and =EXCLUDE= are omitted
   from the DSL; =[:raw]= covers them. Position: add only if a house project asks.
10. *=trusted_schema=OFF= impact.* With it OFF, "SQL functions and virtual tables that
    have not been security audited" (i.e. application-defined functions) cannot be used
    by views, triggers, CHECK/DEFAULT clauses, generated columns or index expressions
    (docs pragma). Whether any house schema needs a UDF inside a DEFAULT is unknown.
    Position: default OFF (sqlite.org's recommendation); =core/open!= =:trusted-schema?
    true= opts back in; a test asserts that a DEFAULT calling a UDF fails under OFF.
11. *=PRAGMA optimize= on close.* Recommended by sqlite.org for long-lived connections;
    cost on huge databases unknown. Position: opt-in =:optimize? true= on =close!=.
12. *Statement cache size and invalidation.* A per-connection LRU keyed by SQL text
    (default 100 entries?) — memory vs. prepare cost is unmeasured. Position: 128 entries,
    cleared by =migrate!= and by =exec!=; measure in the live smoke.
13. *Worker-thread mode.* One connection per worker is documented (docs bs3 threads.md);
    whether the house needs it (long analytical queries) is unknown. Position: out of
    scope; the driver namespace is the seam.
14. *Large IN lists / bulk inserts.* 32766 parameters per statement; =json_each(?)= with a
    JSON array parameter or a temp table are the standard workarounds. Position:
    =core/insert-many!= chunks rows in one transaction; =[:in x coll]= with > 32766 values
    is a dsl-error suggesting =[:in x [:json-each ...]]=.
    Shipped: =query/execute!= chunks a DSL insert transparently (=dsl/render-chunked=,
    =:max-params= override for tests); =[:in x coll]= switches to =json_each(?)= above 500
    values (=:in-json-threshold=), so no IN list ever approaches the parameter limit.
15. *Rows with duplicate column names.* =SELECT a.id, b.id= yields one =id= key in the row
    object (last wins) — better-sqlite3's =expand()= disambiguates by table, node:sqlite
    cannot. Position: the DSL requires aliases when a select would collide (renderer
    detects duplicate result names and raises dsl-error); =expand= is not exposed.
    Shipped: implemented for names the renderer can see (columns, aliases); =*= and
    un-aliased expressions are not checked.
16. *=synchronous= visible value after WAL switch.* On the connection that *switched* to WAL
    the pragma still reads 2; a *new* connection reads 1 (=(local)= §4.1). Position:
    =core/open!= sets WAL then re-reads =synchronous= and reports the effective value in
    =driver-info=; document that the switching connection keeps FULL until reopened.
17. *=busy_timeout= vs. =SQLITE_BUSY_SNAPSHOT=.* In WAL, a DEFERRED transaction that read
    and then writes after another writer committed gets =SQLITE_BUSY_SNAPSHOT= immediately
    (no wait). Position: =:immediate= default (§7.6) avoids it; document the code.
18. *node-sqlite3 (sqlite3 npm) deprecation date.* The README states deprecated /
    unmaintained without a date; 6.0.1 was published 2026-03-12 (npm). Position:
    irrelevant to the decision; recorded for the record.

* 9. Implementation (as shipped)
Namespaces under =src/sqlite_cljs/=; every database operation returns a promesa promise
that is already settled (§1.5); renderers and predicates are pure. The driver is loaded
lazily by =sqlite-cljs.core= only. An earlier sketch had a separate =driver= namespace and
named the DML renderer =query=; the shipped layout below is the reference.

** 9.1 =sqlite-cljs.core= — the ONE interop namespace (connection + driver binding)

|-----------------------------------------------+-----------------------------------------------------------------------------------------------------------|

(true) :journal-mode (:wal for files) :require-journal-mode? (true) :synchronous :trusted-schema? (false) :cache-size (128)=; =:effective= reports the values SQLite answered (journal mode, synchronous, foreign keys, busy timeout, trusted schema) |
| =(close! d opts)=, =(open? d)=, =(in-transaction? d)= | idempotent close (=:optimize? true= runs PRAGMA optimize); synchronous predicates                  |

** 9.3 =sqlite-cljs.dsl= — DML renderer (pure)
=(render q opts)= → ={:sql :params}=; =(render-chunked q opts)= → vector of statements;
=(render-expr e opts)=; =(render-literal e)= (DDL literal mode); =(statement-kind q)=;
=type-names=, =default-in-json-threshold= (500), =default-max-params= (32766). Grammar: §6.3.

** 9.4 =sqlite-cljs.ddl= — DDL renderer (pure)
=(render d opts)= / =(render-table-def d opts)= → ={:statements [..]}=; per-statement
=create-table-sql create-index-sql create-view-sql create-trigger-sql alter-table-sql
drop-sql=, fragments =column-sql constraint-sql type-sql=, =def-kind=, =def-name=,
=expected-columns= (for =migrate!= drift), vocabularies =strict-types all-types fk-actions
conflict-clauses default-keywords=. The introspection helpers sketched earlier
(=table-info!=, =introspect!=, =diff=, =lint=) are not shipped.

** 9.5 =sqlite-cljs.migrate=
=(migrate! d defs opts)= (§6.4), =(status! d)=, =(validate defs)= (pure), synchronous
introspection internals =object-type*= and =table-columns*=.

=argument-error=, =dsl-error=, =config-error=, =migration-error=), =error-data=,
=error-type=, =sqlite-code=, =constraint-error?=, =busy-error?=; also
=sql-string-literal= (literal mode, §6.3.9), =version-vec=, =version>==.
